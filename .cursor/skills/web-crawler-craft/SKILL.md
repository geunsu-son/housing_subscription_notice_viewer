# Web Crawler Craft

## 상태

`ver0` draft. 3가지 수집 패턴(차단 강한 사이트, RSS 본문 충분, 블로그·GraphQL)으로 절차를 검증했습니다.  
사이트별 스크립트는 예시에 포함하지 않습니다. 반복 크롤이 필요해지면 Script 분리를 검토합니다.

## 목적

웹에서 데이터를 수집하거나 크롤러를 구현할 때, 대상·범위·수집 경로·구현·검증을 일관된 순서로 수행합니다.

크롤이 필요한 경우에만 HTML·브라우저 자동화를 선택하고, 결과는 재사용 가능한 스키마와 한계 기록을 함께 남깁니다.

## 사용 시점

- 특정 사이트·목록·상세 페이지에서 데이터 수집
- 기존 크롤러의 파싱 오류·차단·구조 변경 대응
- API 없는 공개 페이지의 정기 수집 설계
- 수집 결과의 스키마·검증 방법 정의

## 입력

- 수집 목적과 최종 사용 맥락
- 대상 URL 또는 사이트 식별 정보
- 필요한 필드와 출력 형식(JSON, CSV, DB 등)
- 수집 빈도·허용 지연·샘플 범위
- 인증·지역·언어 등 접근 조건(있는 경우)

목적에 불필요한 필드는 수집하지 않습니다.

## 절차

### 1. 요청 정리

다음을 한 문장씩 정리합니다.

- 무엇을 왜 수집하는가
- 어떤 레코드 단위로 결과를 원하는가
- 완료와 실패를 어떻게 구분하는가

필드 목록이 불명확하면 최소 스키마를 제안하고 가정을 명시합니다.

### 2. 수집 경로 검토

다음을 순서대로 확인합니다.

1. 공식 API·Open Data·export
2. RSS·sitemap·구조화 피드
3. SPA 내부 API 직접 호출
4. 정적 HTML 파싱
5. 브라우저 자동화

더 안정적인 경로가 있으면 그 경로를 우선 채택하고, 크롤을 선택한 이유를 기록합니다.

**경로가 이미 충분한 경우:** 공식 API·RSS·피드가 요청 필드·범위·신선도를 모두 충족하면, SPA Network 조사·HTML 파싱·브라우저 자동화 단계는 생략할 수 있습니다. 채택 경로와 생략한 단계를 한 줄로 기록합니다.

### 3. SPA·내부 API 직접 호출 검토

동적 렌더·SPA·대시보드·다운로드 UI가 의심되고, **2단계에서 RSS·공식 API로 요구사항이 이미 충족되지 않은 경우**에 수행합니다.

상세 체크리스트는 [`docs/api-direct-call-guideline.md`](../../docs/api-direct-call-guideline.md)를 참고합니다.

#### 3.1 SPA 여부 확인

- 초기 HTML에 목표 데이터가 있는지, 빈 shell + JS인지 확인
- React/Vue 등 SPA 프레임워크 흔적 확인
- 화면 숫자·표·그래프가 JS 로드 후에 나타나는지 확인

#### 3.2 Network에서 내부 API 관찰

1. 개발자도구 Network → XHR/Fetch 필터
2. 대상 동작 수행 (필터 변경, 날짜 변경, 페이지 이동, 다운로드 클릭 등)
3. 발생 요청 기록:
   - URL, HTTP method
   - query/body 파라미터
   - 응답 형식 (JSON, 파일 URL, job id, presigned URL 등)

#### 3.3 인증·재현 가능성

- 세션 쿠키 vs 토큰(JWT 등) 여부
- 로그인 API(`POST /login` 등)로 인증 재현 가능 여부
- 반복·스케줄 실행 시 세션 의존을 줄일 수 있는지

**내부 API 직접 호출을 우선 고려:**

- 응답 JSON에 필요한 필드가 포함됨
- 인증을 코드로 재현하거나 토큰·쿠키를 안전하게 재사용 가능
- 반복 실행·배치·페이지네이션 파라미터화가 필요함
- 기존 UI 자동화가 타이밍·모달·레이아웃 변경으로 자주 실패함

**브라우저 자동화를 유지 검토:**

- CAPTCHA, 강한 봇 탐지, 디바이스 핑거프린팅
- 응답 암호화·난독화로 역공학 비용이 큼
- HMAC 등 동적 요청 서명이 재현 어려움

#### 3.4 구현 메모 (내부 API 채택 시)

- 비공식 API 스펙 변경에 대비한 fallback 경로
- presigned URL은 발급 즉시 다운로드
- job 폴링은 완료 조건·최대 대기·중단 조건 명시
- 자격 증명은 `.env`·시크릿 매니저 등에 저장, 만료 시 재로그인

검토 결과를 `SPA 여부 / 내부 API 후보 / 채택 경로 / fallback` 형태로 기록합니다.

### 4. 사전 조사

대상 사이트를 짧게 조사합니다.

- `robots.txt`, 이용약관, robots 메타
- 목록·상세·검색·페이지네이션 구조
- 동적 렌더·무한 스크롤·AJAX 여부
- 차단 신호(429, 403, CAPTCHA, 빈 shell HTML)
- 요청 빈도·캐시·스냅샷 필요성

조사 결과는 구현 전에 공유합니다. 접근이 부적절하거나 허가가 필요하면 크롤을 중단하고 대안을 제시합니다.

### 5. 범위와 스키마 설계

- 수집 URL 범위와 제외 범위
- 레코드 스키마(필드명, 타입, nullable, 출처)
- 식별 키와 중복 처리 규칙
- 페이지네이션·상세 진입 규칙

스키마 예시:

```json
{
  "source_url": "string",
  "fetched_at": "ISO-8601",
  "title": "string",
  "published_at": "ISO-8601 | null",
  "raw_snippet": "string | null"
}
```

### 6. 도구와 추출 전략 선택

사이트 특성에 맞게 선택합니다. ver0에서는 라이브러리를 고정하지 않습니다.

| 상황 | 일반적 선택 |
|---|---|
| 공식·내부 JSON API 확인됨 | HTTP 클라이언트로 API 직접 호출 |
| 정적 HTML, 단순 링크·텍스트 | HTTP 클라이언트 + HTML 파서 |
| SPA지만 내부 API 미확인, Network 조사 필요 | 브라우저로 Network 관찰 후 API vs UI 재판단 |
| 클릭·스크롤·렌더 대기 필요, API 재현 불가 | 브라우저 자동화 |
| 대량 목록·규칙적 사이트맵 | 크롤 프레임워크 후보 검토 |

추출 전략은 다음 우선순위를 따릅니다.

1. 공식·내부 API JSON 응답·피드
2. JSON-LD·구조화된 embed 데이터
3. 의미 있는 data 속성·안정 컨테이너
4. 텍스트 패턴·정규식(최후 수단)
5. 브라우저 UI 조작(최후 수단)

### 7. 구현

구현 시 포함할 항목:

- 명시적 요청 정책(간격, 재시도, 타임아웃, User-Agent)
- 페이지네이션 종료 조건
- HTTP·파싱 오류 처리
- 빈 결과·부분 파싱 감지
- 원문 URL·수집 시각 기록
- 샘플 모드(소량 URL로 먼저 검증)

차단·인증 실패가 반복되면 무한 재시도하지 않고 중단합니다.

### 8. 검증

다음을 확인합니다.

- 샘플 레코드 N건의 필드 완전성
- 목록 첫·중간·마지막 페이지 또는 페이지네이션 경계
- 날짜·숫자·통화 정규화
- 중복·누락·빈 shell HTML
- 실패 URL과 오류 유형

검증 결과는 통과·실패·미확인을 구분합니다.

### 9. 출력 작성

아래 형식을 기본으로 사용합니다.

```md
## 수집 요약

- 목적: ...
- 대상: ...
- 범위: ...
- 수집 경로: 공식 API / 내부 API / RSS / HTML / 브라우저
- 출력: ...

## SPA·내부 API 검토

- SPA 여부: ...
- 관찰한 엔드포인트: ...
- 채택 경로와 이유: ...
- fallback: ...

## 사전 조사

robots·약관·구조·차단 신호를 요약한다.

## 스키마

필드 정의와 식별 키를 적는다.

## 구현

도구, 추출 전략, 요청 정책, 페이지네이션을 적는다.

## 검증

샘플 결과, 통과·실패 항목, 엣지 케이스를 적는다.

## 한계와 가정

수집하지 않은 항목, 구조 변경 시 취약 지점, 다음 확인이 필요한 사항을 적는다.
```

코드가 결과물이면 README 또는 주석에 위 항목을 반영합니다.

## 완료 조건

- 수집 목적과 범위가 명확함
- API·피드 등 대안을 검토함
- SPA·동적 UI 대상이면 내부 API 직접 호출 가능 여부를 검토함
- 브라우저 자동화를 선택한 경우, Network 조사 또는 재현 불가 사유가 기록됨
- robots·약관·요청 정책을 확인함
- 스키마와 식별 키가 정의됨
- 추출 전략과 도구 선택 이유가 기록됨
- 샘플 검증과 실패 케이스가 구분됨
- 한계·가정·수집하지 않은 항목이 명시됨
- 불필요한 범위 확장·우회 시도가 없음

## 향후 Script 후보

- robots.txt·sitemap 초기 스캔
- JSON-LD·메타 태그 추출
- 페이지네이션 URL 생성·검증
- 샘플 레코드 스키마 검증
- 요청 간격·재시도 래퍼

현재 ver0에서는 도구와 사이트를 고정하지 않습니다. 같은 사이트·같은 스키마가 반복될 때 Script 분리를 검토합니다.
