# API 직접 호출 방식 검토 가이드

> 크롤러/자동화 스크립트를 만들 때, 파일 다운로드나 데이터 수집이 필요한 경우
> 브라우저 자동화(UI 조작) 대신 **내부 API 직접 호출**이 가능한지 먼저 검토하기 위한 문서.

이 문서는 `web-crawler-ver0` 예시의 SPA·내부 API 검토 절차를 보강하는 참고 자료입니다.

---

## 1. 핵심 개념

대부분의 SPA(Single Page Application) 기반 웹사이트는 아래 구조로 동작한다.

```
브라우저가 빈 HTML + JS 로드
  → JS가 실행되며 내부 API 호출 (예: GET /api/campaigns/summary)
  → 서버가 JSON 응답
  → JS가 JSON을 화면에 렌더링 (표, 그래프, 다운로드 버튼 등)
```

화면에 보이는 모든 것(요약 숫자, 표, 그래프, "다운로드" 버튼 결과물)은
**이미 구조화된 JSON 데이터를 예쁘게 포장한 결과물**일 뿐이다.
즉 "다운로드"는 특별한 케이스가 아니라, 웹페이지가 동작하는 일반적인 방식의 한 사례다.

### 비동기 파일 생성 패턴 (다운로드에서 흔함)

1. 버튼 클릭 → `POST /report-files` 등으로 생성 요청
2. 서버가 작업을 큐에 등록, job id 또는 상태값 반환
3. 프론트가 완료될 때까지 폴링
4. 완료 시 서버가 결과 파일을 S3 등에 업로드
5. presigned URL(임시 서명 URL) 반환 → 그 주소로 실제 다운로드

## 2. 브라우저 자동화 vs API 직접 호출

| 구분 | 브라우저 자동화 (Selenium 등) | API 직접 호출 |
|---|---|---|
| 실행 경로 | 브라우저 렌더링 → JS 이벤트 → API 호출 | 코드가 API를 바로 호출 |
| 속도/자원 | 브라우저 로딩·렌더링 대기 필요 | HTTP 요청/응답만 존재, 훨씬 가벼움 |
| 안정성 | 모달·팝업·레이아웃 변경에 취약 | UI 요소와 무관, 응답 구조만 영향받음 |
| 반복 처리 | 매번 UI 조작 필요 | 파라미터로 반복 자동화 쉬움 (`--date`, `--since` 등) |
| 확장성 | 페이지네이션/필터 처리 번거로움 | 쿼리 파라미터로 간단히 처리 |
| 안정 리스크 | 화면 변경 시 셀렉터 깨짐 | UI와 무관하지만 비공식 API라 스펙 변경 가능 |

**결론**: 결과물(데이터)은 동일하지만, API 직접 호출이 속도·안정성·자동화 적합성 면에서 우월한 경우가 많음.

## 3. 에이전트를 위한 검토 체크리스트

크롤러를 만들 때 파일 다운로드 로직이 필요하면, 먼저 아래 순서로 API 직접 호출 가능 여부를 확인한다.

### Step 1 — 대상 사이트가 SPA 구조인지 확인
- 페이지 소스에 실제 데이터가 있는가, 아니면 빈 껍데기 + JS인가
- React/Vue 등 프레임워크 흔적이 있는가

### Step 2 — Network 탭에서 실제 API 호출 관찰
1. 크롬 개발자도구(F12) → Network 탭 → XHR/Fetch 필터
2. 대상 동작 수행 (다운로드 클릭, 필터 변경, 날짜 변경, 페이지 이동 등)
3. 그 순간 발생하는 요청 확인:
   - 요청 URL, HTTP method
   - 요청 파라미터/body
   - 응답 구조 (JSON 형태, 파일 URL 포함 여부, job id 방식인지)

### Step 3 — 인증 방식 파악
- 세션 쿠키 기반인지, 토큰(JWT 등) 기반인지 확인
- 쿠키/토큰 유효기간 확인
- 로그인 자체도 API로 처리 가능한지 확인 (`POST /login` 등)

### Step 4 — 재현 가능성 판단
아래에 해당하면 API 직접 호출 방식 채택을 우선 고려:
- [ ] 응답이 JSON이며 필요한 데이터를 그대로 포함
- [ ] 인증이 쿠키/토큰 재사용 또는 코드로 로그인 처리 가능
- [ ] 반복 실행(스케줄러, 배치)이 필요한 작업
- [ ] 기존 방식(UI 자동화)에서 타이밍/모달 대기 등으로 실패가 잦았던 이력

아래에 해당하면 브라우저 자동화 유지 검토:
- [ ] API가 CAPTCHA, 강한 봇 탐지, 디바이스 핑거프린팅 등으로 보호됨
- [ ] 응답이 암호화/난독화되어 있어 역공학 비용이 큼
- [ ] 요청 시그니처(HMAC 등 동적 서명값)가 필요해 재현이 어려움

### Step 5 — 구현 시 유의사항
- 비공식 내부 API이므로 UI 변경 시 예고 없이 스펙이 바뀔 수 있음 → 실패 시 fallback 로직 고려
- presigned URL은 유효시간이 있으므로 발급 즉시 다운로드
- 인증 토큰/쿠키는 안전하게 저장 (.env, 시크릿 매니저 등), 만료 시 재로그인 로직 포함
- 스케줄러(cron, Prefect 등)로 무인 실행할 경우, 로그인 자체를 코드가 처리하는 방식을 우선 고려 (크롬 세션 의존 배제)

## 4. 적용 범위 — 다운로드 외 다른 데이터도 동일

다운로드 API는 예외가 아니라 일반적인 패턴의 한 사례이므로, 아래도 동일한 방식으로 접근 가능:

- 대시보드 요약 숫자 → `GET /api/stats/summary` 형태
- 리스트/표 데이터 → `GET /api/campaigns?page=1` 형태 (페이지네이션 파라미터화 용이)
- 그래프 데이터 → `GET /api/chart-data?from=...&to=...` 형태

HTML 파싱(BeautifulSoup 등) 방식과 비교하면:
- 이미 구조화된 JSON이므로 파싱 불필요
- 페이지네이션/필터가 파라미터로 처리되어 스크래핑보다 안정적
- 화면에 표시되지 않는 원본 필드(내부 ID 등)까지 얻을 수 있는 경우도 있음

## 5. 요약 원칙 (에이전트 판단 기준 한 줄 요약)

> **"파일을 다운로드하거나 화면 데이터를 가져와야 하는 크롤러를 만들 때는,
> UI 자동화를 먼저 설계하지 말고 Network 탭에서 내부 API 존재 여부부터 확인한다.
> API가 존재하고 인증 재현이 가능하다면, 그 방식을 기본으로 채택한다."**
